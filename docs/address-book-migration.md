# 地址簿数据库升级

Issue #9 新增地址簿版本、共享关系和连续变更日志。该 schema 依赖每次库存写入与变化日志在同一事务中提交，因此升级必须采用停写方式。

升级步骤：

1. 备份 SQLite 数据库文件及其 `-wal`、`-shm` 文件。
2. 停止并排空所有连接同一数据库的旧版 `hbbs`、API 服务和其他写进程。
3. 确认旧进程全部退出后，只启动一个新版本实例完成迁移与地址簿 backfill。
4. 等待日志出现 `Database migrations complete`，再启动其余同版本实例。
5. 验证 `/api/health`、认证登录、`GET /api/ab` 与 sysinfo/heartbeat。

不要让新旧二进制对同一 SQLite 数据库滚动混跑。旧版本不会写地址簿变化日志，应用级锁无法修复这种跨版本写入。新版本会用数据库旁的 `.migration.lock` 跨进程序列化迁移、修复、backfill 和启动完整性检查；该锁不能替代停止旧版写进程。

回滚时先停止所有新版本实例，再恢复升级前的完整数据库备份，不能只回退二进制后继续使用已升级数据库。

## 限流与代理部署

API 限流以服务端 TCP 连接看到的直连 peer IP 为准，不解析也不信任 `X-Forwarded-For`。若约 300 台以上设备共享同一 NAT 或反向代理出口，应按单出口设备规模调高 `telemetry_peer_capacity` 和 `telemetry_peer_refill_per_minute`；认证配额也应按同一出口的并发用户规模评估。也可以在可信反向代理侧实施额外限流，但不要依赖客户端可伪造的转发头覆盖应用内限流。
